# Ouroboros

**Category:** Reversing | **Difficulty:** Hard | **Points:** 650 | **Solves:** 1 | **Flag:** `Null0rigin{you_found_where_it_eats_its_own_tail}`

> Chain note: this challenge is stage 5 of the Null Origin reversing chain. Flags use the chain-internal `Null0rigin{...}` format (note the **zero**), distinct from the platform `NullOriginCTF{...}` format.

## Challenge Description

> You have seen this handwriting before. It was never designed for you. That is simply how this thing writes.

At first that reads like poetic nonsense. By the end it's the clearest hint in the challenge.

## Initial Analysis

Three files:

- **`ouroboros`** — ELF64, static, stripped, **21 MB**. The name is a hint: the serpent that eats its own tail. The binary literally reads `/proc/self/exe` ~730,000 times, sliding a 16-byte window across its own body.
- **`verify`** — ELF64, static, stripped, 736 KB. The actual checker. Usage: `verify <candidate> <password>`.
- **`ouroboros.shadow`** — a Unix shadow entry for user `vault`, SHA-512-crypt (`$6$`).

21 MB for a stripped binary means something is stuffed inside. `readelf` reveals a custom section `.ouroborosdump` that accounts for almost all of it. `strings` on it gives a wall of **1,200 decoy flags**:

```text
Null0rigin{cycle_return_loop_0000}
...
Null0rigin{spiral_tail_wind_coil_fold_1199}
```

procedurally generated from a 14-word vocabulary (`cycle, return, loop, close, recur, spiral, tail, wind, coil, fold, mirror, ring, again, echo`), numbered `0000`–`1199`, with filler "ASSAY SHEET" text mixed in. (`verify` also keeps a `.ouroboros.strikes` counter — three wrong tries and it locks; just `rm` the file.)

## The Vulnerability / Core Concept

### What `verify` actually checks

Decompiling `verify` (main at `sub_401740`) reveals **two independent SHA-256 checks** that both must pass:

1. `SHA256(argv[1]) == 771ecbf65d76ff25534a8230d479a3a42f201c3884af3a3c771cabd6bfe3fe51` — the candidate (the flag). Find the preimage.
2. `SHA256(crypt_sha512(argv[2], "$6$2/MNIR6I/CBsE7Pa$")) == 0277644f…` — confirms the password is the `vault` user's real shadow credential. Secondary: not needed to find the flag.

So the flag is whatever string hashes to `771ecbf6…`.

### The elaborate rabbit hole: the GF(2) cascade

The `ouroboros` binary (not `verify`) implements a 5-layer verification cascade. Each layer generates a matrix from a splitmix64 PRNG seeded from a state `var_1e8`, computes BLAKE2s hashes of the candidate, and checks `M · x == t` over GF(2). GF(2) linear algebra is a well-understood technique, so the natural move is to dump the matrices and solve. `dump_matrix.py` (a gdb script, break at `0x401d17` right after the splitmix64 row fill) scrapes every row + target bit; `solve.py` / `solve2.py` run Gaussian elimination over the dumps.

The output was **garbage** — not "wrong flag," actual non-printable bytes.

### The catch: candidate-dependent seeds

At the end of each layer the binary re-finalizes the next layer's seed `var_1e8` from the candidate's own BLAKE2s expansion (`sub_4037f0(&var_278, &var_1e8)`). So **each layer's matrix depends on the candidate you're testing.** Confirmed by dumping the layer-2 seed under two candidates:

- `AAAA…` → seed `3f a8 2c …`
- `BBBB…` → seed `d1 09 f7 …`

Different candidates, different matrices. The cascade is **non-invertible by design** — `ouroboros` only *verifies*; it can't be run backwards to produce the flag. (That's why `solve.py`/`solve2.py` are kept as documented dead ends.)

### Dead end: brute-forcing the decoy format

Maybe the flag *is* a decoy-format string whose SHA-256 happens to match? A hashcat run on a GPU box tried k = 3..8 words from the 14-word vocab × `NNNN = 0000..9999` (plus no-number variants) — roughly 81 million candidates. **Zero matches.** The flag is not a generated string.

### The actual trick: read the room

Back to the description: *"You have seen this handwriting before. It was never designed for you. That is simply how this thing writes."* The decoys show the *style*, not the substance; they were generated by the binary for itself; "that is simply how this thing writes" — the *thing* writes in its own words. Look at `ouroboros`'s own usage/flavor text: `"you found where it eats its own tail"`. Snake-case it, wrap it, check the hash:

```python
candidate = "Null0rigin{you_found_where_it_eats_its_own_tail}"
hashlib.sha256(candidate.encode()).hexdigest()
# 771ecbf65d76ff25534a8230d479a3a42f201c3884af3a3c771cabd6bfe3fe51  ✅
```

Exact match. The flag was in the binary's own usage string the whole time.

## Exploitation

No exploit to build — once you see it, you see it:

```bash
# 1. Extract the usage string
strings ouroboros | grep "eats"          # you found where it eats its own tail
# 2. Format as a flag, snake_cased
# 3. Verify against the known target hash
python3 -c "import hashlib; \
c='Null0rigin{you_found_where_it_eats_its_own_tail}'; \
print(hashlib.sha256(c.encode()).hexdigest() == \
'771ecbf65d76ff25534a8230d479a3a42f201c3884af3a3c771cabd6bfe3fe51')"   # True
```

To also make the binary print "accepted," you'd crack the `vault` shadow password for `argv[2]` (chain-wide standard: `contractor`, set-on seam `85`; see `../credential_standard.txt`) — but that doesn't change what the flag is. `solve.py`, `solve2.py` and `dump_matrix.py` are included to show the GF(2) machinery and *why* it fails here.

## Key Takeaways

- **Don't let the complexity of the verifier distract you from the preimage.** When a binary checks `SHA256(input) == CONST`, you can't break SHA-256 — you brute a known space or find the plaintext elsewhere (source, strings, logic).
- **A massive corpus of decoys is deliberate misdirection** — the flag probably isn't one of them; it establishes a *plausible* format to lure you into the wrong keyspace.
- **"Handwriting" means style, not substance** — the format is shown to you, the content comes from the binary's own text.
- **Always dump the same matrix/seed under two different inputs before building a linear solver.** If the rows change, the system depends on your input and can't be inverted externally — it's a verifier, not a keygen.
